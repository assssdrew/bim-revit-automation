# Цепочка «Revit → xlsx → Google»: как устроена и где ломалась

## Поток данных

```
ui_schedules.ps1  (WinForms, вкладка «Задание», кнопка «Собрать задание»)
  │  1. пишет run.cfg (report_dir, список наборов) и запускает Revit Batch Processor (RBP)
  ▼
export_schedules.py  (IronPython внутри Revit, сводная модель)
  │  2. для каждой ViewSchedule с «Пустые»/«Без знач» и для четырёх замечаний без этого суффикса
  │     (0_Ошибка типоразмера, 1_Классификатор_999, 16.0_Корпус_Кириллица, 17.0_Секция_Кириллица)
  │     пишет NNNN.tsv (UTF-8 BOM, TAB),
  │     и последним — один файл export.txt: [result] (exported=N …), [manifest] («файл<TAB>имя спецификации» …),
  │     [catalog] (все спецификации и связи). Прежние выгрузки (manifest.txt / export_result.txt / catalog.txt)
  │     читаются так же: bvs_export_result.ps1
  ▼
build_assignment.ps1  (PowerShell, без Revit и без Excel)
  │  3. assignment_export_stream.ps1: потоково читает tsv → _sections\<РАЗДЕЛ>.jsonl,
  │     считает счётчики по (модель, спецификация), историю (задание_история.txt)
  │  4. assignment_xlsx.ps1: пишет xlsx через lib\DocumentFormat.OpenXml.dll
  │     листы: Сводка, ЭОМ/СС/ОВ/ПД/ПТ/ВК/ОТ/ХС, Динамика; группировка строк (2 уровня)
  │     и ТЕ ЖЕ строки/форматы сохраняет в google_push_payload.json
  │  5. bvs_assignment_guard.ps1: проверка zip/XML/OpenXmlValidator; битый файл удаляется
  ▼
ui_schedules.ps1 → Push-GoogleAssignment → push_google.ps1
  │  6. читает google_push.cfg (google_push_cfg.ps1), payload (google_payload_lib.ps1),
  │     добавляет clear[] (разделы без замечаний) и hide[] (Динамика), POST JSON
  ▼
служебное/google_push/Code.gs  (Apps Script Web App, привязан к таблице)
     7. под LockService полностью пересоздаёт листы: значения (текст/числа), цвета, ширины,
        объединения, группы строк; отвечает JSON {"ok":...}
```

Отчёт шагов «Сводная»/«Разделы» (`Export-ReportXlsx` в UI) пишется без Excel: `report_xlsx.ps1` собирает xlsx как zip с XML (System.IO.Compression), листы Сводка / Вставлено / Параметры / Пропуски из CSV `insert_schedules.py`, строки спецификаций свёрнуты под строкой модели. Excel COM (`excel_isolated.ps1`) остался только в запасной сборке задания (`build_assignment.ps1`) и в чтении xlsx для Google без готового payload (`push_google.ps1`).
и как запасной путь push_google, если payload-файла нет. Само «задание» собирается без Excel.

## Известные ограничения (не менял)

- Сборка и отправка идут в потоке UI (окно «замирает»); Excel-путь чтения xlsx для Google по ячейкам очень медленный — нужен только если нет payload.
- Apps Script: один запуск ≤ 6 минут; на очень больших разделах (десятки тысяч строк) группировка строк по одному вызову может не уложиться.
- `google_push_payload.json` лежит в служебной папке прогона (не рядом с xlsx) и не привязан к нему хешем; `build_assignment.ps1` удаляет старый payload перед сборкой, поэтому рассинхрон возможен только при ручных копированиях.

## История и журнал замечаний

**Срезы (`задание_история.txt`).** Каждая сборка — отдельный срез (8-я колонка `BuildId` = `yyyy-MM-dd HH:mm:ss`). «Прошлое» в Сводке — предыдущая *сборка*, а не вчерашний день. Исправленное записывается **нулём** (ключ «модель + спецификация + параметр» был в прошлом срезе, спецификация проверена сейчас, строк нет). Галочка «Одна сборка в день» в окне (или `-CollapseDay`) оставляет только последнюю сборку за день. Старше 60 дней хранится последний срез дня. Старый формат читается (срез = дата + 00:00:00).

**Проверено / не проверялось.** Выгрузка из Revit пишет в `[manifest]` (`export.txt`) и пустые спецификации (`*empty*`). Спецификация есть в выгрузке, строк нет — «исправлено». Спецификации нет в выгрузке (убрана из списка) — «не проверялось»: замечания не закрываются, колонка в Сводке не показывается. Если Revit не нашёл ни одной спецификации, ничего не закрывается.

**Журнал (`задание_журнал_<проект>.txt`, на проект; прежний общий `задание_журнал.txt` переносится в PROJ — `Invoke-LedgerPerProjectMigration`).** Замечание = строка спецификации: модель + спецификация + семейство и типоразмер + наименование. Поля: найдено, последний раз видели, статус (open/fixed), дата исправления, сколько раз возвращалось. Вернулось — снова open, помечается «Новое».
- Листы разделов (xlsx): колонки «Статус / Найдено / Исправлено / Дней»; «Замечаний» — только открытые, «Исправлено» — число исправленных; исправленные серым, остаются `-KeepFixedDays` (30) дней; раздел остаётся, даже если открытых нет.
- «Динамика»: каждое исправленное за период замечание строкой (найдено, исправлено, дней); остаток из старой истории, которого журнал не знает, — строкой «без детализации».
- Сводка: «6 (7) ↓2 ↑1» — сейчас 6, было 7, исправлено 2, новых 1 с прошлой сборки.
- Google получает только открытые замечания (7 колонок), как раньше.
- Первая сборка с журналом: все замечания «найдены» в этот день (журнал начинается с неё), «Новое» не ставится.

**Ограничения.** Если модель-связь не загружена в сводной, её замечания исчезнут из выгрузки и будут закрыты как исправленные (отличить от реального исправления нельзя); вернутся как «Новое», когда связь загрузят. Замечание = типоразмер: если параметр заполнили у части экземпляров, строка остаётся до полного исправления.

## Порядок спецификаций

Колонки Сводки, спецификации внутри моделей на листах разделов и в «Динамике» идут одинаково (и в xlsx, и в Google, т.к. payload строится из тех же строк). Порядок набора из Revit API получить нельзя (браузер сортирует по имени строкой, блоки `schedule_sets.txt` не отсортированы), поэтому: номер в начале имени сравнивается как версия (0 < 1 < 2.1 < 4.4 < 5.7 < 13 < 14.7 < 16.0 < 16.1 < 17.0 < 17.1 < 99), дальше имя без суффикса `_Пустые` / `_999` / `_Без знач…` (учтена опечатка «Без значния»), дальше «Пустые», затем «999», затем «Без значения». Спецификации без номера — в конце по имени. Реализация: `Get-CheckSortKey` / `Sort-CheckNames` в `assignment_export_stream.ps1` (ординальное сравнение).

**Пары в шапке Сводки.** Если после сортировки рядом стоят «…_Пустые» и «…_Без значения» одной проверки (одинаковое имя без суффикса), между их колонками в строке 2 нет вертикальной границы; в строках с числами граница обычная. В xlsx — два стиля границы (без правой / без левой) у ячеек шапки; в Google — `meta.pairCols` в payload и `applyHeaderPairs_` в `Code.gs` (после общих границ). **Code.gs нужно переопубликовать.**

## Колонка «Параметр»: что считается проверяемым параметром

`export_schedules.py` пишет в 4-й столбец `[manifest]` только **проверяемый** параметр спецификации, а не все её фильтры. Правило (`choose_check_params`): проверяет пустоту фильтр с условием «не имеет значения» (`HasNoValue`) или «равно» пустой строке; остальные фильтры — это отбор («Код по классификатору» с условием «имеет значение», материал `ADSK_Материал наименование`, «Связанный файл…») и в «Параметр» не попадают. Служебные поля (связанный файл, семейство и типоразмер, наименование, количество, категория) исключаются по имени. Сравнение — по точному имени (кроме «Связанный файл: …»): раньше слово «Наименование» искалось внутри имени, и «ADSK_Материал наименование» ошибочно считалось служебным — у спецификаций 13_Материал после разового исправления фильтров «Параметр» остался бы пустым. Запасной путь, если ни один фильтр не подошёл по условию: все фильтры, кроме явного отбора (`HasValue`, содержит, не равно…); если и таких нет — как раньше все не служебные.

**Уточнение правила (по реальным фильтрам 57 спецификаций, `tests/fixtures/filters_before_fix.txt`).** (1) «Код по классификатору» никогда не берётся в запасных вариантах: проверяемым бывает только при «равно пусто»/«не имеет значения» (1_Классификатор_Пустые); «NotEqual 999» — отбор. (2) «ADSK_Марка изделия» с «не имеет значения» при другом проверяющем фильтре — отбор (спецификации систем 2.x/3.x/4.x). (3) Если проверяющих фильтров несколько (5.1/6.1/7.1 «Детали воздуховодов»: размер и диаметр) — показывается тот, чьё имя совпадает с темой из имени спецификации (второй сегмент: Диаметр, Ширина, Высота, Длина, Материал, Номер здания…); нет совпадения — все через запятую. Тема «Тип системы» сопоставляется с «Имя системы» (Revit не фильтрует по типу системы), «Клас-я системы» — с «Классификация систем». **Нижний регистр кириллицы.** В IronPython 2.7 `str.lower()` меняет только ASCII: «Ширина».lower() остаётся «Ширина» (это и показала колонка «Тема спеки» в реальной выгрузке — тема была с заглавной), поэтому сравнения темы с именами полей и `ADSK_Марка изделия` с `adsk_марка изделия` молча не срабатывали, а часть случаев работала случайно (по совпавшему корню слова). Теперь везде `lower_text()` (A–Z, А–Я, Ё заменяются вручную), родной `.lower()` в функциях выбора параметра запрещён тестом. В `фильтры_спецификаций.txt` есть колонки «Тема совпала с полем» (да/нет у проверяющих фильтров) и «Диагностика» (работает ли родной `lower()` на этом Python). Тема разбирается обычными строковыми операциями, **без регулярных выражений** (lookbehind в IronPython 2.7 на живом Revit не сработал: тема не находилась, хотя в CPython всё верно; тест `test_ironpython_compat.py` теперь запрещает lookbehind в скриптах Revit). В `фильтры_спецификаций.txt` добавлены колонки «Тема спеки (распознана)» и «Выгружено» (время выгрузки — видно, свежий ли файл). Тема берётся из имени без разбора префикса: «П», регистр и вид пробелов (в именах Revit бывают неразрывные) не важны — раньше префикс срезался регулярным выражением только по обычным пробелам, и при другом префиксе тема не находилась, а в «Параметре» оставались оба условия «не имеет значения» (5.1/6.1/7.1 «Детали возд-в»). Ключи истории и журнала от «Параметра» не зависят.

**Где неоднозначно:** условие для «Пустые» (оно может быть «равно пустому» или другим) на реальных спецификациях не проверено. Поэтому выгрузка пишет один файл `фильтры_спецификаций.txt` в служебную папку прогона (все фильтры каждой спецификации: поле, условие, значение, роль «ПРОВЕРЯЕМЫЙ»). Если «Параметр» где-то неверен — пришлите этот файл.

**Ключи не меняются.** Ключ истории (`Param`) строится по заголовкам колонок, ключ журнала — по модели, спецификации, семейству и наименованию; показываемое имя параметра (`ParamName`) в ключи не входит, поэтому замена правила не создаёт «новых» замечаний (проверено тестом).

**Замечания без суффикса «Пустые»/«Без значения».** Раньше `is_issue_schedule` смотрел только на эти слова, и проверки без суффикса в отчёт не попадали. Явный список `LITERAL_ISSUE_PARAMS` в `export_schedules.py` (ключ — номер и название без пробелов и «_», регистр через `lower_text`, опечатка «кирилица»; префикс стадии не важен). Параметр взят из фильтров сводной (`tests/fixtures/align_dumps`):

| Спецификация | Фильтр-проверка | Параметр |
|---|---|---|
| `0_Ошибка типоразмера` | `ADSK_Наименование` Equal «Ошибка типоразмера» | `ADSK_Наименование` |
| `1_Классификатор_999` | `Код по классификатору` BeginsWith `999` | `Код по классификатору` |
| `16.0_Корпус_Кириллица` | `ADSK_Номер здания` HasValue | `ADSK_Номер здания` |
| `17.0_Секция_Кириллица` | `ADSK_Номер секции` HasValue | `ADSK_Номер секции` |

Это не проверка пустоты: `is_check_filter` их не видит, а «Код по классификатору» в запасном пути запрещён — без списка у «999» параметр был бы пустым. Каждая строка — замечание; в «Значении» текст колонки параметра (для `ADSK_Наименование` колонка иначе попадала в «Наименование»; «ADSK_Материал наименование» не трогается). Пустой результат — `*empty*` в `manifest.txt`. Номера 0, 1, 16.0 и 17.0 уже в общих номерах справочника, поэтому спецификации есть в каждом разделе и в «Выборочно». Порядок (`Sort-CheckNames`): номер как версия (0 раньше 1, 16.0 раньше 16.1, 17.0 раньше 17.1); при одном номере «Пустые», затем «999», затем «Без значения». Склейка шапки пары — только «Пустые»/«Без значения», не «999». `Code.gs` не менялся. Не выгружаются `*_Все`, `Уникальные_*` и «Пров     Ошибка типоразмера».

## Эталон режима «Всё» (tests/baseline)

## Выборочная выгрузка («Выборочно»): выгрузка из Revit

Включается только ключом `assign_scope=partial` в `run.cfg`; без него `export_schedules.py` работает как раньше (проверено `tests/test_export_partial.py` и `tests/test_baseline.py`). Ключи: `assign_specs=` (имена спецификаций через `|`) и `assign_models=` (имена связей как в отчёте, без `.rvt`, сравнение без регистра и без пути).

В выборочном режиме выгружаются только выбранные спецификации и только строки выбранных моделей (колонка «Связанный файл»). В `[manifest]` добавляются строки `*scope*<TAB>partial и `*pair*<TAB>модель<TAB>спецификация` — пары, проверенные в этом прогоне, **включая пустые результаты**: пара «модель × спецификация» считается проверенной, если спецификация найдена в сводной модели и выбрана, а связь модели загружена (по `RevitLinkType.GetLinkedFileStatus() == Loaded`) либо в выгрузке нашлись её строки. Не загруженная связь пар не даёт — её замечания закрываться не должны. Выбранная, но отсутствующая в модели спецификация пар не даёт и попадает в `[result]` (`missing_specs=`).

Всегда (и в «Всё») пишется раздел `[catalog]`: `spec<TAB>имя` для всех проверочных спецификаций и `model<TAB>имя<TAB>loaded|unloaded` для всех связей — по нему UI строит списки, а сборка вычищает из буфера переименованное и удалённое. В «Всё» `[manifest]` и `[result]` — как прежние `manifest.txt` и `export_result.txt`; в «Выборочно» в `[result]` добавляются `partial=1`, `pairs=`, `missing_specs=`, `unloaded_models=`.

## Выборочная выгрузка: сборка по буферу (`assignment_partial.ps1`, `-Partial`)

**Идея — «виртуально полная выгрузка».** Сборка в режиме «Выборочно» берёт строки проверенных в этом прогоне пар («модель + спецификация», из `*pair*` в `[manifest]`) и добавляет к ним прежнее состояние всех остальных пар из буфера. Дальше всё идёт тем же кодом, что и в «Всё»: Сводка, листы разделов, xlsx и payload для Google собираются из этой полной картины, поэтому непроверенные модели остаются в отчёте как были.

**Файл состояния** — один на историю (проект): `<история>_состояние.txt` рядом с историей. До фазы 7 это были три файла `<история>_буфер.txt`, `_проверки.txt`, `_каталог.txt`; строки разделов — ровно их строки:

| раздел | что в нём |
|---|---|
| `[buffer]` | замечания по всем парам: Section, Model, Check, Param, ParamName, Family, Item, Value |
| `[checks]` | Model, Check, BuildId — когда пара проверялась в последний раз; Model = `*` — спецификация проверена целиком (полная выгрузка) |
| `[catalog]` | каталог последней выгрузки (`export.txt [catalog]`: спецификации и связи со статусом) — из него UI строит списки; в выгрузке каталога нет — остаётся прежний |

Файл пишется целиком через временный (`.tmp` + подмена). Прежние три файла читаются, пока не перенесены; если прежний файл новее файла состояния (откат на старую версию и обратно) — берётся он. Перенос (`Invoke-PartialStateMigration`, из `Invoke-ProjectStateMigration` при открытии окна): резервная копия `проект\_backup_<время>` (как в фазе 5, вне автоочистки), запись, проверка перечитыванием, переименование прежних в `.migrated_<дата>`; повторный запуск ничего не делает. Эталон `tests/baseline_partial` (снят на коде фазы 6) проверяет, что «Выборочно», «Всё» и «Динамика» дают тот же результат.

**Что считается «проверено».** Только пары из `*pair*`. Журнал (`Update-IssueLedger -CheckedPairs`) закрывает замечание только проверенной пары; непроверенные не получают ни `LastSeen`, ни «Новое»/«исправлено». В историю (`New-CurrentSlice`) срез пишется полный (непроверенные пары переносятся из буфера с теми же числами), нули («исправлено») — только для проверенных пар; ↓↑ и «Динамика» считаются по событиям журнала, поэтому ложных не дают.

**Режим «Всё» не меняется:** он по-прежнему целиком заменяет картину выгрузкой; после сборки только дописывает файлы состояния (буфер = вся выгрузка, проверки = `*` по каждой спецификации). Сбой записи состояния не ломает сборку (предупреждение). Если выгрузка выборочная, а сборка без `-Partial` (или наоборот), сборка останавливается с понятным сообщением — иначе отчёт получился бы неполным.

**Первый «Выборочно» без буфера** засевает буфер из открытых записей журнала и последнего среза истории (параметр и дата проверки берутся из среза). Нет ни журнала, ни истории — сборка просит сделать полную выгрузку. При засеве число строк пары может отличаться от истории (журнал не хранит дубликаты строк), тогда в «Прошлом» будет видно «N (M)» — это не «исправлено».

**Что убирается из буфера.** Спецификации и модели, которых нет в каталоге последней выгрузки (переименованы/удалены), уходят из отчёта сразу, без синего нуля. Записи журнала при этом остаются `open`, как и в «Всё» для убранной спецификации — они просто не показываются. Незагруженная связь остаётся в каталоге (`unloaded`), её пары не проверяются и не закрываются. Без каталога (очень старый выгрузчик) ничего не вычищается.

### Свежесть и Google в режиме «Выборочно»

Только при `-Partial` (в «Всё» ничего из этого нет: ни колонки, ни `dim`, ни полей payload).

- **Сводка**: последняя колонка «Проверено» — самая старая дата проверки среди пар модели в видимых колонках спецификаций (`<история>_проверки.txt`; запись `*` — вся спецификация проверена полной выгрузкой). Красноватая заливка, если старше 7 дней на дату сборки. Ячейки пар, которые в этой сборке не проверялись, — серым шрифтом (`dim` в `formats`: в xlsx — серый шрифт, в Google — `setFontColor('#999999')` в `Code.gs`).
- **Листы разделов**: в заметке первой строки — какие модели не обновлялись в этой сборке (сколько спецификаций из скольких и дата последней проверки). Одинаково в xlsx и Google.
- **Лимит Apps Script (6 минут).** В `google_push_payload.json` для выборочной сборки: `partial: true`, листы — Сводка и разделы моделей, проверенных в этом прогоне (+ скрытая «Динамика», она не отправляется), и явный `clear` — только затронутые разделы, где замечаний не осталось. `push_google.ps1` использует этот `clear` вместо «все разделы, которых нет в payload», поэтому незатронутые разделы в Google не очищаются. xlsx при этом всегда полный (все разделы).
- **Code.gs нужно переопубликовать** (поддержка `dim`; без неё серого шрифта в Google не будет, остальное работает).

Вставка не создаёт дубль, если в модели уже есть спецификация под другим написанием.

Спеки в моделях уже переименованы разовым прогоном, `schedule_sets.txt` обновлён. Чтобы ключи истории/журнала/буфера (модель + спецификация + параметр) не изменились, имя «…Без значния» приводится к «…Без значения» при чтении: `ConvertTo-CanonicalSpecName` (`assignment_export_stream.ps1`; запасное определение в `assignment_ledger.ps1` и `assignment_partial.ps1`) применяется в `Read-History`, `Read-IssueLedger`, `Read-PartialBuffer`, `Read-PartialChecks`, `Read-ExportCatalog`, `Read-NamesFromLedgerAndHistory`, при разборе `manifest.txt`; `export_schedules.py` (`canon_spec`) сравнивает выбранные спеки с именами в Revit в каноническом виде; `insert_schedules.py` ищет спеку в файле-источнике и считает «хвост» имени в каноническом виде. Тест: `tests/test_chain.py::SpecRenameKeepsHistoryTests`. `Code.gs` не менялся.

## «Выборочно»: пары «модель × спецификация»

**Слева** дерево «раздел → модель». Галочка модели или раздела — «выгружать эту модель»; при отметке все её спецификации отмечаются (дальше пользователь снимает лишние). **Клик** по модели или разделу (выделение, не галочка) показывает справа спецификации этого узла: у модели — её набор, у раздела — объединение наборов моделей раздела; ничего не выделено — «Выберите модель или раздел». **Галочки спецификаций хранятся для каждой модели отдельно** (`$script:AsgPicks`: модель → спека → да/нет). У раздела галочка ставит/снимает спеку у всех его моделей, где она есть; частичное состояние — `Indeterminate` и пометка «[частично]» (щелчок по «частично» отмечает у всех). «все»/«ничего» справа действуют только на выделенный узел. Подписи: «<модель или раздел>: выбрано N из M» и «Всего к выгрузке: P пар, K моделей» (K — отмеченные модели хотя бы с одной парой).

**Набор спецификаций модели** — `Get-PartialModelSpecInfo($ModelNames, $Project)` (`assignment_partial_ui.ps1`) спрашивает `Get-ProjectModelSpecs` (`project_config.ps1`): у модели есть отметки в распределении — берутся они; иначе раздел по имени файла и объединение по его моделям; иначе набор не определён — у модели все спецификации, **причина** (`Why`) пишется в строку статуса, подсказку и `partial_sets.log`. Сопоставление имён — `Get-PartialSpecKey` = `Get-ProjectSpecKey` (регистр, пробелы, префикс стадии, «значния» не важны). Прежний источник (`schedule_sets.txt`, `список_спецификаций.txt`) не читается. *Причина старой ошибки «57 из 57»:* окно передавало разбор не того файла, и набор не находился ни у одной модели.

**Выгрузка** — набор пар: окно пишет `assign_pairs.txt` (модель TAB спека, UTF-8 BOM) в служебную папку прогона и `assign_pairs_file=` в `run.cfg`; `export_schedules.py` читает его через .NET и выгружает строки только выбранных пар (`assign_models`/`assign_specs` остаются как объединение, без файла — прежнее пересечение). Не выбранные пары не проверяются, их замечания не закрываются. **Сохранение** (`ui_settings.txt`): `asgmodels=` (отмеченные модели), `asgpairsfmt=1` и строки `asgpair=<модель>|<спека>` (`<модель>|*` — модель была в выборе: новые модели отмечаются целиком); прежние `asgmodels=`/`asgspecs=` читаются (одни отметки спек на все модели). Тесты: `tests/test_partial.py::PartialUiLogicTests`, `tests/test_export_partial.py`, `tests/test_ui_layout.py::LinkedListsWiringTests`.

## Раскладка папки «отчеты»

`отчеты\` — только итоговые `.xlsx`; `отчеты\история\` — постоянные файлы (история, журнал, буфер/проверки/каталог «Выборочно»), не удаляются; `отчеты\служебные\<время прогона>\` — файлы прогона (выгрузка Revit, manifest, диагностика фильтров, `google_push_payload.json`, CSV вставки спецификаций), автоочистка старше 30 дней (`auxkeepdays=` в `ui_settings.txt`); `отчеты\операции\` — CSV и дампы служебных .bat, старше 30 дней удаляются. Реализация — `report_layout.ps1` (`Get-ReportLayout`, `Initialize-ReportLayout` = создание папок + миграция старых файлов без удаления + автоочистка, `New-RunAuxDir`, `Remove-RunBulk`). Окно строит рабочую папку прогона сразу в `служебные\<время>` (раньше `%TEMP%\verif_schedules_*`, удалялась после сборки): `export_schedules.py`/`insert_schedules.py` пишут туда через .NET; после успешной сборки удаляются только `*.tsv` и `_sections`. `build_assignment.ps1 -AuxDir` кладёт payload в служебную папку (фильтры туда же пишет выгрузка, одним файлом `фильтры_спецификаций.txt`; без `-AuxDir` фильтры копируются рядом с xlsx, как раньше), `push_google.ps1` получает путь через `-PayloadPath`. В папку проекта эти файлы больше не копируются. Полный перечень файлов — `ФАЙЛЫ_ОТЧЕТОВ.md`. Тесты: `tests/test_report_layout.py`.


## Распределение спецификаций и профиль объекта (настройка проекта)

**Единственный источник** «какие спецификации в какие модели/разделы» — файл `отчеты\проект\распределение_<префикс моделей>.txt` (префикс — часть имени моделей до первого «_», например `PROJ`; вкладка «Распределение», `project_config.ps1` + `project_dist_ui.ps1`). Его читают: окно (вкладки «Сводная» и «Разделы», «Выборочно») и `insert_schedules.py`. Перед «В сводную»/«В разделы» окно пишет готовый план `служебные\<прогон>\plan.txt` (`Get-InsertPlanLines`/`Write-InsertPlan` в `project_config.ps1`) и передаёт его в `run.cfg` (`plan_path=`): скрипт в Revit берёт набор каждой модели из плана и файл настройки не разбирает. Правила плана — ровно прежние правила `insert_schedules.py` (`tests/test_insert_plan.py` сравнивает оба пути на PROJ и SampleSite). Разбор файла в `insert_schedules.py` (`load_project` …, помечен LEGACY) остался запасным путём: плана нет (старое окно), он не записался или повреждён — и для «Посчитать элементы». Прежние зашитые таблицы «раздел → пакеты» и импорт из `schedule_sets.txt` удалены; настройка пуста, пока не нажата «Загрузить спецификации и модели». Парсер файла продублирован в PowerShell и IronPython (запасной блок LEGACY в `insert_schedules.py`); совпадение проверяется тестами. Файл пишется явным «Сохранить» (`Commit-DistDirty` → `Save-DistProject`) либо служебной записью уже подтверждённого состояния; пустой путь к настройке — запуск не выполняется (`Get-ProjectRunBlocker`, `project_path_blocker`).

**Раздел по имени файла — одно правило** (`Get-ModelSectionFromName` в `project_config.ps1`, `section_code_from_name` в `insert_schedules.py` и `set_assembly_code.py`; «Выборочно» использует то же): код ищется только как «_КОД_», регистр не важен, коды ОВ/OV, ПД/PD, ВК/VK, ПТ/PT, ОТ/OT, ХС/HS, ИТП/ITP, ЭОМ/EOM, СС/SS, АВТ/AVT, ХЦ/HC; если в имени нет «_КОД_» и нет маркера TASK/AR/KR/TH/BASE — запасной вариант по имени папки модели (папка RVT пропускается); токен вида `_IOS_|_ORG_<КОД>_`, которого нет в таблице разделов, в распределение не входит (колонки «Неизв.» нет): модель пропускается и при «Загрузить», и «из сводной», и в «В разделы»/«Посчитать»; в статусе может быть «Пропущено N моделей без целевого раздела». Старые строки UNKNOWN в файле не показываются и не роняют чтение, из файла уходят только при явном «Сохранить». Сводная (`SVOD`/`СВОД`) — не раздел. Признаки IOS/ИОС/ВИС/TASK не используются. Модель без кода — не инженерная: в настройку не попадает, в таблице не показывается, раздел ей назначить нельзя, в распределении и пробной вставке не участвует. (Не менялись: `build_assignment.ps1`, `assignment_export_stream.ps1` — разбор имён связей для отчёта-задания.)

Формат файла (UTF-8 BOM):

```
[project]   stage= template= models_dir=
[sections]  КОД<TAB>Название               (справочно)
[models]    имя<TAB>КОД                    (только инженерные)
[specs]     имя (без префикса стадии)
[inproject] имя спецификации               (спеки, отмеченные «В проекте» — по каждой спецификации; нет раздела — в проекте все)
[summary]   имя спецификации               (спеки, идущие в сводную; нет раздела — все из «В проекте»)
[groups]    спека<TAB>группа               (только ручные переносы)
[cells]     модель<TAB>спека<TAB>1|0<TAB>a|m|x<TAB>число элементов   (a — авто, m — вручную, x — не определено)
```

**«В проекте».** Группы отмечает BIM-менеджер по BEP; без отметки группа не распределяется по моделям, не вставляется и не попадает в сводную. Группа = ведущий номер + первое слово (`1_Классификатор`, `7.8_Диаметр`); спецификация без хвоста подписана «(основная)». Сводная получает «В проекте» ∩ `[summary]` (колонка «Сводная»; `Get-ProjectSummarySpecs`, `project_summary_specs`).

**Профиль.** Имена спецификаций хранятся без префикса стадии; имя вида в Revit = стадия + 8 пробелов + название; префикс стадии общего файла (например РД) заменяется выбранной стадией. В значениях фильтров `{СТАДИЯ}`/`{STAGE}` подставляется при вставке (`apply_profile`: `definition.SetFilter`). Шифра и `{ШИФР}` нет. Один набор файлов обслуживает разных заказчиков: меняется только файл проекта.

**Чтение общего файла** — `read_template_specs.py` (RBP) пишет `template_specs.tsv`. **«Распределить по моделям»** — `insert_schedules.py`, `mode=prefill`: для модели одно открытие, одна `TransactionGroup`; все отмеченные спецификации копируются одним `CopyElements` (`insert_batch`), профиль применяется, элементы считаются `FilteredElementCollector(document, view.Id)` (запасной способ — строки таблицы − 1; оба способа не сработали — ячейка «не определено»), группа откатывается, модель не сохраняется. Если пачка не вставилась, спецификации вставляются по одной, причина — в журнале RBP (`WARN prefill … falling back to one-by-one`). Время открытия источника, вставки, профиля, подсчёта и отката по каждой модели — в `prefill.tsv` (строка `#МОДЕЛЬ`), журнале RBP и `распределение.log` служебной папки прогона (там же общее время прогона).

Что не менялось: логика «Выборочно» (пары, буфер), файлы в `отчеты\история\`, выгрузка.


## Раскладка папки и переносимость путей

В корне: `Проверочные спецификации.vbs`, `ИНСТРУКЦИЯ.txt`, `servers.cfg`, `отчеты\`, `служебное\`. В `служебное\`: `скрипты\` (все `*.ps1`/`*.py` окна и задач Revit), `lib\`, `choose_models.ps1` (его вызывает окно), `google_push\`, `rbp_rsn_patch\`, `разработка\` (тесты, документация; `инструменты\` — служебные .bat дампа и сравнения фильтров). Отдельной сборки нет.

**Переносимость.** Все пути — только от расположения файлов: `.vbs` ищет `ui_schedules.ps1` в подпапках `служебное` (в файле нет кириллицы — WSH читает .vbs в ANSI, имена папок не зашиты); `$ToolDir` скриптов — `служебное\скрипты`; корень, служебная папка и `lib` — `Get-BvsRootDir`/`Get-BvsServiceDir`/`Get-BvsLibDir`, корень отчётов — `Get-ReportRootDir` (`report_layout.ps1`): `<корень>\отчеты`, не внутри `служебное`. `servers.cfg` читается из корня, `google_push.cfg` — из `служебное\google_push`, dll — из `служебное\lib`. Служебные `.bat` (`служебное\разработка\инструменты`) начинаются с `pushd "%~dp0"` (cmd не делает UNC текущей папкой). Пути пользователя (общий файл, папка моделей, сводная) — в `%LOCALAPPDATA%\BatchRvt\batch_verification_schedules` (`ui_settings.txt`), там же `run.cfg` запуска; Python-скрипты RBP читают только `%LOCALAPPDATA%` (зашитых путей к профилям и серверам нет), task-скрипты передаются RBP полным путём от `$ToolDir`. dll при отказе загрузиться с сетевой папки копируется в профиль пользователя. Проверка без Revit: `служебное\скрипты\ui_schedules.ps1 -SelfCheck` (печатает `TOOLDIR`, `REPORTDIR`, `SELFCHECK OK` или `MISSING=…`, код 3). Тесты: `tests/test_portability.py`.

## Версия Revit для запуска RBP (`revit_versions.ps1`)

Версию не угадывают по имени/пути (раньше `Guess-Year`, с адресами серверов в коде): `--revit_version` передаётся **всегда**, год берётся из самих моделей — для `.rvt` из `BasicFileInfo` («Format: 2022»; чтение Microsoft Compound File без Revit, `BvsCompoundFile`, читаются несколько секторов), для `RSN://хост/…` — из `servers.cfg` по хосту (`host|название|год`). Перед запуском (`Resolve-RevitRun`) на всех шагах (Распределение: загрузка и распределение; Сводная, Разделы, Задание) запуск останавливается с коротким сообщением, если: версия модели не определена, модели разных версий, общий файл новее моделей. Общий файл старше моделей — норма (держится в ранней версии, «Только чтение», не сохраняется; при чтении спецификаций открывается в своей версии). Инструменты `align`/`fix`/`replace` (сохраняют модели) и `dump` используют тот же `revit_versions.ps1`: неизвестная, смешанная версия или эталон новее моделей — остановка, `--revit_version` всегда. Тесты: `tests/test_revit_versions.py` (файлы Compound File собираются тестом; настоящий `.rvt` на Linux не проверялся).
